## Context

The HUD is the most constantly visible surface in the game, so its vocabulary does more to establish
setting than anything else in Wave 1.

`PlayerStatusViewModel` already switches its bar labels contextually — `ToggleLabels(bool isCharacter)`
around line 109 swaps `HP:` / `STM:` / `FP:` for the starship set `SH:` / `HL:` / `CAP:`. **A third
label set follows an established pattern here; you are not inventing a mechanism.**

`TargetStatusViewModel` exposes the same `Bar1Label` / `Bar2Label` / `Bar3Label` shape around line 44.
`PlayerStatusPortraitViewModel` is different — its own header comment explains it renders thin Stamina
and FP bars over the portrait and *deliberately omits HP*, because the engine already draws the native
red HP bar on the portrait edge. Respect that; do not add an HP bar to it.

Line numbers are from the time of writing — **locate by symbol, not by line**.

`SWLOR.Game.Server/Service/ShadowrunDisplay.cs` (Wave 0) is the single source of truth:

```csharp
ShadowrunDisplay.GetPhysicalConditionBoxes(int currentHP, int maxHP)      // -> 0..ConditionMonitorBoxes
ShadowrunDisplay.GetStunConditionBoxes(int currentStamina, int maxStamina)
ShadowrunDisplay.GetEdge(int forcePoints)
ShadowrunDisplay.ConditionMonitorBoxes                                    // const
```

## Requirements

1. Add a Shadowrun label set to the character branch of `ToggleLabels`: `PHYS:` / `STUN:` / `EDGE:`
   replacing `HP:` / `STM:` / `FP:`. **Leave the starship branch (`SH:` / `HL:` / `CAP:`) untouched** —
   it is out of scope.
2. Apply the same vocabulary to `TargetStatusViewModel`.
3. Apply it to `PlayerStatusPortraitViewModel` for the bars it actually renders (Stamina and FP →
   Stun and Edge). Do not add an HP/Physical bar.
4. **Keep the numeric `current / max` bar values and the progress fractions exactly as they are.** The
   bars must continue to show real numbers and fill proportionally. Condition-monitor boxes are an
   *additional* way to express the same state, not a replacement for the bar — a player needs to see
   that they are on 43/200 health, not only that four boxes remain.
5. Where a condition-monitor box count adds genuine clarity, surface it through `ShadowrunDisplay`
   rather than computing boxes inline. If you conclude boxes do not fit the existing bar layout,
   **say so in your final message and leave the layout alone** — do not force it.
6. Do not change bar colours, ordering, refresh logic, or the events that drive updates. This is
   vocabulary only.
