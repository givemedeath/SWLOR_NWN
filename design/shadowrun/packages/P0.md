## Context

P0 is Wave 0, solo, and every downstream package (P1–P8) consumes its contract, so its shape must be
settled before Wave 1 opens (`design/shadowrun/ORCHESTRATION.md` wave structure). It is Lead-tier
because getting this shape wrong is expensive to undo across nine dependent packages — not because the
individual mappings are hard.

Per `DECISIONS.md` D2, this is a **reinterpretation of numbers that already mean the right thing**, not
an arbitrary mapping over unrelated values: `ACC`/`EVA` are already composed as `skill + attribute +
gear`, which is exactly how a Shadowrun dice pool is built.

Source formulas being reinterpreted (read these before writing the mapping, in case they've drifted
since this brief was written):

- `ACC = 8 + 2*skillRank + attribute + gearBonus` — `Stat.GetAccuracy`,
  `SWLOR.Game.Server/Service/Stat.cs:1328` (body at line 1330: `return 8 + (2 * level) + stat +
  bonus;`)
- `EVA = 8 + 2*armorRank + AGI + (AC*5 + evasionBonus)` — `Stat.GetEvasion`,
  `SWLOR.Game.Server/Service/Stat.cs:2034` (body at line 2036, same shape as `GetAccuracy`)
- `hitRate = 75 + floor((ACC - EVA)/2) + mods`, clamped to `[20, 95]` —
  `Combat.CalculateHitRate`, `SWLOR.Game.Server/Service/Combat.cs:323` (constants at lines 35–37:
  `BaseHitRate = 75`, `MinimumHitRate = 20`, `MaximumHitRate = 95`)

### The mapping to implement

| SWLOR value | Displayed as | Mapping |
|---|---|---|
| `ACC` | Attack Pool | `round((ACC - 8) / K)` with `K = 8`, giving pools ~2–18 |
| `EVA` | Defense Pool | same divisor |
| `chanceToHit` | `(Pool 12 vs 9)` | replaces the `%` form in combat-log lines |
| `weaponDMG` | DV | direct |
| `HP` / `MaxHP` | Physical condition monitor | `boxes = ceil(HP% * boxCount)` |
| `Stamina` | Stun condition monitor | same formula |
| `FP` | Edge | direct |
| skill rank (1–50) | SR skill rating | `ceil(rank / 8)` giving 1–7 |
| attribute score | SR attribute | divisor chosen to land 1–9 |

This table is the contract every downstream package (P1 feedback suppression, P2 character sheet, P3
HUD/portrait/target, P4 TLK/2DA, P7 glitches) reads display values through. Method names and signatures
should read as a public API, not internal helpers — Wave 1 briefs will be written against whatever
shape lands here.

## Requirements

1. `K` is a **named constant** (e.g. `AttackPoolDivisor` or similar — pick a name that reads as the
   divisor's purpose), never a literal `8` inlined at call sites. It is the single knob governing how
   the whole game reads, and it will be retuned once characters exist at level cap.
2. The condition-monitor `boxCount` is likewise a named constant, not a literal at each call site.
3. Every mapping in the table above gets its own public method on `ShadowrunDisplay` (pool, DV, condition
   boxes, Edge, SR skill rating, SR attribute, and the `(Pool X vs Y)` combat-log formatter). Do not
   collapse distinct concepts (e.g. Attack Pool vs Defense Pool) into one shared method just because the
   arithmetic is identical — downstream callers reference them by gameplay meaning.
4. The mapping must be **monotonic and stable** across the full stat range for every function: as the
   input strictly increases, the output must never decrease. Two `ACC` values that round to the same
   displayed pool but produce visibly different hit rates is the failure players find first — because
   `chanceToHit`/hit-rate math is untouched by P0 (that lives in `Combat.CalculateHitRate`), the display
   layer must not introduce apparent contradictions on its own axis.
5. Tests must assert monotonicity and stability **across ranges** (e.g. loop every integer `ACC` from
   its practical minimum through a level-cap-scale maximum and assert the pool is non-decreasing, plus
   boundary/rounding stability), not spot-check individual hand-picked values. Spot values are fine as
   additional cases, not as the only coverage.
6. Choose `K` and `boxCount` empirically by checking they produce sane pool/box ranges against real
   `ACC`/`EVA`/HP ranges pulled from `Stat.cs`/character data — not by guessing round numbers. Record the
   chosen values and the reasoning (including what range of raw values was checked) in `DECISIONS.md` as
   a new `D<n>` entry, in the existing ADR format (`Decision` / `Why` / `Revisit when`), the moment they
   are chosen — not retroactively.
7. Do not touch `Stat.cs`, `Combat.cs`, `StatType.cs`, or any other file outside the owned set. P0 is
   read-only with respect to the formulas it reinterprets; it wraps them, it does not change them. `EVA`
   and soak changes are P5/P6's job (Wave 2), serialized after P0.

## Project rules that apply

From `AGENTS.md`:

> "Do not use internal initiative, milestone, or phase labels such as `CombatUpgrade` in production
> code identifiers, filenames, namespaces, classes, methods, or comments. Use domain terms that
> describe gameplay behavior, such as ability targeting, ability effects, Leadership, Devices, or the
> specific system being changed."

> "Building or testing `SWLOR.Game.Server` fires a Windows post-build deploy (`SWLOR.CLI.exe -o`) that
> is slow and unnecessary for verification. Always skip it by passing `-p:RunPostBuildEvent=Never` on
> builds, and use a build-once/test-many flow."

From `DECISIONS.md`:

> "Several constants in this project — the display divisor `K`, the wound-modifier free threshold, the
> soak curve — are **empirical values with no derivation from the Shadowrun tabletop rules**. They
> exist only to reconcile Shadowrun vocabulary with SWLOR's existing combat math. Without the reasoning
> recorded here, nobody will be able to reconstruct why they hold their values, and any later attempt to
> retune them will be guesswork."
